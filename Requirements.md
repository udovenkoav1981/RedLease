#### RedLease — a 1-RTT quorum-based distributed lease protocol inspired by Redlock

# Требования к сервису межнодовых lease-блокировок

Сервис предназначен для распределённой блокировки ресурсов между узлами кластера с приоритетом на минимальную latency - в среднем должно быть 1 RTT.

Архитектура представляет собой специализированный quorum-based distributed lease service, оптимизированный прежде всего под минимальную latency.

Сервис должен быть отказоустойчив к отказу 2 узлов.


## Общая модель

- Блокировка имеет формат `key -> lease`.
- Все данные хранятся **только в RAM**.
- Запись на диск не используется.
- Кластер состоит из **5 независимых lock-server узлов**.
- Для успешной операции требуется quorum **3 из 5**.
- Сервис должен продолжать работать при отказе **любых двух узлов**.
- Membership кластера фиксированный: все клиенты должны использовать один и тот же набор из 5 lock-server узлов.


## Failure model

Система рассчитана на:

- crash lock-server;
- restart lock-server;
- потерю до двух lock-server;
- packet loss;
- сетевые задержки;
- временную недоступность отдельных узлов;
- reconnect persistent streams;
- кратковременные scheduler/GC pauses клиента;
- кратковременные сетевые проблемы клиента.

Сервис не пытается сохранять lock state через полный restart всего кластера.

## Основные целевые свойства

```text
Nodes                   5
Quorum                  3
Tolerated failures      2
Maximum TTL             5 s
Typical renew interval  1 s
Maximum active locks    10 000
Storage                 RAM only
Acquire latency         ~1 RTT
Renew latency           ~1 RTT
Consensus leader        отсутствует
Disk persistence        отсутствует
Fencing token           отсутствует
Transport               persistent ordered gRPC streams
```


## Lease

Максимальный TTL:

```text
5 секунд
```

Владелец активной блокировки должен продлевать lease примерно:

```text
каждую 1 секунду
```

Таким образом в нормальном режиме после успешного renew остаётся около 4 секунд запаса до истечения lease.

Основные операции:

```text
Acquire(key, leaseID, ttl)
Renew(key, leaseID, ttl)
Release(key, leaseID)
```

Для фонового доведения числа реплик - для повышения отказоустойчивости конкретного quorum, используется логическая операция:

```text
Attach(key, leaseID, ttl)
```

`Attach` является внутренней операцией протокола и не обязан быть отдельным
публичным RPC. Его точное wire-представление определяется при проектировании
протокола.

Максимальный `ttl` — 5 секунд.

## Lease ID

Каждый lease имеет глобально практически уникальный идентификатор:

```text
leaseID = {
    clientID,
    bootID,
    leaseSeq
}
```

где:

```text
clientID
```

— уникальный ID клиентской ноды 32бит, задаваемый в конфигурации;

```text
bootID
```

— случайный 32бит идентификатор, генерируемый через криптографический RNG при каждом запуске клиентского процесса;

```text
leaseSeq
```

— локальный атомарный счётчик 32бит, начинающийся с нуля после старта процесса.

Таким образом рестарт клиента создаёт новое пространство `leaseID`, а внутри одного процесса уникальность обеспечивается атомарным счётчиком.

## Acquire

Клиент одновременно отправляет `Acquire` на все 5 lock-server узлов.

Каждый server локально атомарно выполняет:

```text
если key отсутствует или его lease уже истёк:
    установить новый lease
    вернуть OK
иначе:
    вернуть BUSY
```

Acquire считается успешным после получения:

```text
>= 3 OK
```

При этом клиенту не требуется ждать оставшиеся два ответа.

Целевая latency успешного Acquire:

```text
примерно 1 network RTT
```

до третьего по скорости lock-server.

### Cleanup после failed Acquire

Если Acquire не получил quorum, клиент не владеет lease, даже если новый
`leaseID` был установлен на одном или двух серверах. Например:

```text
             S1 S2 S3 S4 S5

client A      A  A  A        -> winner, 3/5
client B               B  B  -> loser,  2/5
```

Проигравший клиент обязан немедленно отправить:

```text
Release(key, B.leaseID) -> all 5 servers
```

Cleanup выполняется для всех пяти серверов независимо от того, с каких из них
клиент успел получить `OK`. Это best-effort операция: отсутствие ответа от
отдельного сервера не превращает failed Acquire в успешный и не означает
владение lease.

Если клиент повторяет Acquire, он использует новый `leaseID` и randomized
backoff. Это уменьшает время существования частичного состояния вида `AAA BB` и
снижает вероятность повторного конфликта конкурирующих клиентов.

## Background healing 3/5 → 5/5

Quorum из трёх серверов достаточен для установления владения и немедленного
возврата успешного результата приложению:

```text
minimum quorum  = 3/5
target replicas = 5/5
```

После получения третьего `OK` клиент не ждёт остальные ответы на
latency-critical path. Он продолжает обработку уже отправленных запросов и в
фоне пытается установить тот же `leaseID` на серверах, на которых lease ещё не
установлен. Такое фоновое доведение выполняется на протяжении жизни активного
lease, в том числе после восстановления или restart отдельных серверов.

Логически фоновая попытка имеет вид:

```text
Attach(key, leaseID, ttl)
```

Server может принять `Attach` только если:

```text
key отсутствует
OR lease уже истёк
OR current.leaseID == requested.leaseID
```

Активный lease с другим `leaseID` никогда не перезаписывается. В частности,
наличие quorum у клиента не даёт ему права принудительно заменить чужой lease
на отдельном сервере.

Успешный `Attach` увеличивает только число серверных реплик. Он сам по себе:

- не устанавливает владение, если клиент ранее не получил quorum;
- не продлевает клиентский `validUntil`;
- не должен задерживать успешный `Acquire` после получения 3/5.

Продлить клиентский `validUntil` может только успешный quorum `Renew`.
Background healing прекращается после `Release` или после утраты клиентом
локальной validity lease.

Цель healing — перейти из временного состояния:

```text
3/5 → 4/5 → 5/5
```

Lease, оставшийся только на трёх серверах, безопасен с точки зрения
единственности владельца, но после отказа одного из этих серверов может потерять
возможность получить quorum для `Renew`. Lease, доведённый до 5/5, способен
продолжать `Renew` при отказе любых двух серверов.

## Renew

Владелец примерно раз в секунду параллельно отправляет:

```text
Renew(key, leaseID, ttl)
```

на все 5 серверов.

Server может продлить lease только если:

```text
current.leaseID == requested.leaseID
AND
lease ещё не истёк
```

Уже истёкший lease нельзя воскресить через `Renew`.

Renew считается успешным только после:

```text
>= 3 OK
```

Успешный Renew начинает новый TTL на каждом ответившем сервере.

Если quorum не получен, клиент продолжает считать действительным предыдущий успешно подтверждённый lease до его локального срока окончания и может повторять Renew.

## Release

Release имеет вид:

```text
Release(key, leaseID)
```

Server удаляет lock только если текущий `leaseID` совпадает с переданным.

Старый владелец поэтому не может удалить lock нового владельца.

Обычный `Release` может быть best-effort и не обязан находиться на latency-critical path.

При необходимости API может дополнительно иметь вариант:

```text
ReleaseAndWaitQuorum()
```

который ждёт подтверждения минимум от 3 серверов.

## Время

Для измерения времени используется стандартный Go:

```go
time.Now()
time.Since()
time.Time.Add()
time.Time.Before()
```

Пока `time.Time` остаётся внутри процесса, Go использует встроенную monotonic-компоненту времени.

Временные значения между клиентами и серверами не передаются.

В частности клиент не отправляет:

```text
client timestamp
absolute expiresAt
monotonic timestamp
```

Server получает только длительность:

```text
ttl
```

и самостоятельно устанавливает локальный deadline:

```go
deadline := time.Now().Add(ttl)
```

Таким образом часы разных серверов не требуется напрямую сравнивать.

NTP используется как обычная системная синхронизация времени, но алгоритм не основывается на сравнении wall-clock timestamp разных машин.

## Локальная validity на клиенте

При Acquire клиент фиксирует:

```go
start := time.Now()
```

После получения quorum:

```text
validUntil =
    start + TTL - safetyMargin
```

То есть время, потраченное на Acquire, вычитается из срока, в течение которого клиент считает lease действительным.

Для Renew используется аналогичная схема:

```go
renewStart := time.Now()
```

После получения quorum:

```text
validUntil =
    renewStart + TTL - safetyMargin
```

Если Renew не получил quorum, `validUntil` не увеличивается.

После достижения `validUntil` клиент обязан считать lease потерянным и не начинать новые защищённые операции.

## Семантика без fencing token

Fencing token не используется.

`leaseID` защищает сам lock-service от:

- stale `Renew`;
- stale `Release`;
- случайного воздействия старого владельца на новый lease.

При этом сервис не гарантирует остановку операции, которая была начата владельцем до истечения lease и завершилась уже после его истечения.

Гарантия сервиса формулируется как distributed lease:

> Клиент может начинать новые защищённые операции только пока его локальный lease считается действительным.

Приложение обязано прекратить начало новых защищённых операций после потери lease.

## Persistent streams

Каждая клиентская нода поддерживает по одному постоянному ordered gRPC stream к каждому из пяти lock-server:

```text
client
  ├── stream → server1
  ├── stream → server2
  ├── stream → server3
  ├── stream → server4
  └── stream → server5
```

Streams независимы друг от друга.

Замедление или потеря одного server не должны блокировать коммуникацию с остальными.

Через один stream multiplex'ятся операции по множеству ключей:

```text
Acquire
Renew
Release
Acquire
Renew
...
```

Persistent stream используется для:

- устранения connection setup из hot path;
- сохранения порядка операций;
- уменьшения количества RPC overhead;
- эффективного обслуживания тысяч одновременно активных leases.

## Поведение после restart lock-server

Так как состояние хранится только в памяти, после crash/restart server теряет все свои leases.

Чтобы старые leases, существовавшие до crash, не пересеклись с новыми, рестартовавший server не имеет права участвовать в quorum сразу после запуска.

Он входит в quarantine:

```text
REJOIN_DELAY >
    MAX_TTL + safetyMargin
```

При `MAX_TTL = 5s` server ждёт более 5 секунд перед началом обработки Acquire/Renew как полноценный участник кластера.

Во время quarantine server не учитывается клиентами как источник успешного quorum.

Благодаря quorum 3/5 два одновременно перезапускающихся или отказавших узла не останавливают работу оставшихся трёх.

## Отказ всего кластера

Все данные memory-only.

После одновременного падения всех пяти узлов состояние блокировок полностью теряется.

Предполагается, что полный restart кластера занимает больше максимального TTL, то есть больше 5 секунд.

Следовательно к моменту возврата кластера все ранее существовавшие leases считаются заведомо истёкшими.
