# RedLease — требования к сервису межнодовых lease-блокировок

Этот документ определяет, **что** должен гарантировать RedLease.

- [`Architecture.md`](Architecture.md) описывает, **как** эти требования
  реализуются принятой архитектурой.

Параметры и гарантии из этого документа являются нормативными. Изменения
архитектуры не должны ослаблять их без отдельного согласования.

## 1. Назначение и границы

RedLease предоставляет распределённые краткоживущие блокировки ресурсов между
узлами кластера с приоритетом на минимальную latency.



Блокировка имеет вид:

```text
key -> leaseID
```

- key и leaseID генерируется на стороне клиента
- сервер ни как не проверяет уникальность leaseID
- межнодовая уникальность leaseID обеспечивается клиентом

Базовый API:

```text
Acquire(key, leaseID)
Renew(key, leaseID)
Release(key, leaseID)
GetTTL()
```

- в `Acquire`, `Renew` и `Release` отсутствует TTL;
- TTL задаётся только в конфигурации lock-server при его старте;
- TTL остаётся неизменным всё время жизни server process;
- `GetTTL()` возвращает настроенный на сервере TTL;
- при старте клиент сравнивает TTL всех серверов — значения должны быть равны;
- изменение TTL существующего deployment не поддерживается; если такая
  возможность потребуется, она будет проектироваться отдельно.


## 2. Сервис должен:

- выдерживать отказ любых двух lock-server узлов;
- обслуживать до 10 000 одновременно активных leases;
- хранить всё состояние только в RAM;
- не использовать запись на диск;
- обеспечивать Acquire и Renew примерно за один network RTT в штатном режиме.
- сихронизация времени между клиентами и серверами не требуется

## 3. Архитектурые ограничения на которы мы согласны

- cервис не сохраняет lock state через полный restart всего кластера
- настройка ServerId и ClientId делается заранее гарантированно правильно
- Membership кластера фиксированный. Все клиенты должны использовать один и тот же набор  lock-server узлов.
- TTL невозможно настроить для отдельной lease
- TTL одинаков на всех lock-server и не меняется в существующем deployment
- Quorum это понятие исключительно клиента, клиент должен отслеживать какие его Quorum еще живы.


## 4. Гарантии и ограничения безопасности

Система должна сохранять следующие инварианты:

- опеспечивать принятие Quorum клиентом однозначным, эксклюзивным образом
- активный чужой lease никогда не заменяется принудительно;
- истёкший lease не воскрешается через Renew;
- stale Renew и stale Release не воздействуют на lease с другим `leaseID`;
- background healing не продлевает клиентскую validity;
- restart lock-server не позволяет создать пересекающееся владение до истечения
  ранее существовавших leases.

Глобальный fencing token не предоставляется. `leaseID` защищает состояние самого
lock-service от stale Renew и Release, но сервис не гарантирует остановку
операции, начатой владельцем до истечения lease и завершившейся после него.

Гарантия сервиса формулируется как distributed lease:

> Клиент может начинать новые защищённые операции только пока его локальный
> lease считается действительным.

Если downstream-ресурсу нужна защита от уже выполняющейся stale-операции, она
должна обеспечиваться отдельно, например версией, CAS или транзакционной
проверкой.
